# 2026-11-02 — Phase 5 Modules 8–9 (`registry.rs`, `kopeng/stats.rs` Typed Errors)

Follow-up of `2026-11-01_phase5_documents_errors.md`.

## `RegistryError`
- Variants: `InvalidPath`, `IdNotRegistered`, `PathNotRegistered`, `Io`, `RemovalAborted { path, reason }`, `Task`, `Database(#[from] DatabaseError)`. Implements `Serialize` (the three Tauri commands return it directly) and `From<RegistryError> for String` for the callers still on `String`.
- Decision (maintainer): the single-implementation `ProjectRepository` trait / `SqliteProjectRepository` are replaced by free functions `list_projects()`, `find_project_by_id(id)` (new `db_get_project_by_id`) and `find_project_by_path(path)` (existing `db_get_project_by_path`). The callers that scanned the whole list to find one project (flag resolver, profiler ×2, supervisor state, MCP `caller_project` / `task_process_key`) now query by key.

## Fallbacks removed
- `load_projects` turned any SQLite failure into an empty list, so a database error looked like "no projects" (`get_projects` → empty sidebar, MCP → "project not registered", watcher/telemetry/supervisor ticks → nothing to do). `list_projects` and `get_projects` return the error; the background ticks (service telemetry, continuous profiler, agent state watcher) log ERROR and skip the tick; `notify_projects_updated` and the watcher log ERROR and emit nothing; MCP `list_projects` returns an `isError` result.
- `add_project` registered any string: a path without a final component (`/`) got an empty name, and relative, missing or non-directory paths were accepted. It now requires an absolute path to an existing directory and stores the canonical path.
- `remove_project` discarded the knowledge export result, the init-state deletion, the snapshot ref listing and each `git update-ref -d`, and only warned on artifact purge failures, then deleted the project anyway (an export failure lost the project's tasks, debt and journal). Every step before the deletion now aborts with `RemovalAborted` and the project stays registered. The init-state deletion moved into `db_remove_project`'s transaction. The command is async and runs on the blocking pool (it ran file and git work on the main thread).
- Spec 08 §2.7 described a `prompt_agent` fallback that scans running processes when `project_path` is omitted; the code already rejects it. The spec now states the required project.

## Removal assistant
Decision (maintainer): when the automatic removal fails, the UI shows the failure and offers to cancel or to use an agent. The agent resolves the failures, then a Delete approval button (like the approval cards) deletes the project, closes the agent and ends the cycle. Keep it simple; the flag system may carry the state.

- Flow: `remove_project` aborts → `App.vue` shows `RemovalFailedModal` (failure report; Cancel / Resolve with agent). Cancel keeps the project registered. Resolve calls `launch_project_removal_agent(project_id, purge_traces, failure_report)` (flag_resolver.rs), which records a pending `removal` initialization flag (`metadata_json`: `RemovalFlagMetadata { purge_traces, failure_report }`, replacing an earlier pending one) and launches `removal-resolver` through `launch_flag_resolution_agent` (template `flag_resolve_removal`, skill `oneship-core`); the chat overlay opens on it.
- Closure: the agent calls the new MCP tool `complete_project_removal { summary }`. It is accepted only from `removal-resolver` on a project with a pending removal flag, and blocks on a user approval (`approval_type: "project_removal"`; `ApprovalRequestModal` labels the buttons Delete / Cancel). Approved → `registry::execute_project_removal` retries the full removal; success deletes the project (the flag cascades) and stops the agent, failure returns the new report to the agent. Rejected → flag dismissed, project kept, agent stopped. Other text → feedback to the agent.
- The approval wait of `request_approval` was extracted into `await_user_approval`, shared by both tools; the pending-approval row is now deleted on every outcome in one place.
- The `[! REMOVAL]` badge on the card relaunches the agent (same flag path); dismissing it cancels the removal. `compute_project_state` lists `removal-resolver` while the flag is pending.
- Scoping fix found on the way: `resolve_initialization_flag` resolved any flag id, including other projects' flags. It now requires a flag of the caller's own project, and rejects `removal` flags.
- Layers: prompt `templates/prompts/flag_resolve_removal.md`, `oneship-core` SKILL.md tool list, specs 01 §1 and 12 (§6 tool list, §6.7 caller-scoped tools).
- Known limit: a pending approval restored from SQLite after a reload has no `approval_type` (not stored in `pending_approvals`), so it shows Approve Phase / Reject; the responses are the same (`Approved` / `Rejected`).

## `kopeng/stats.rs` (`StatsError`, module 9)
Decisions (maintainer): the context window comes from the runner manifest; `get_all_active_agent_metrics(_cmd)` is deleted (no caller, and it returned N copies of `get_agent_metrics(None, None)`).

- `StatsError` variants: `HomeUnavailable`, `Io`, `StatuslineJson`, `UnattributedStatusline`, `UnknownStatuslineAccount`, `AccountMismatch`, `UnknownAccount`, `InvalidConfig`, `ProbeFailed`, `RunnerManifest`, `Task`, `Registry`, `Database`, `Accounts`. Implements `Serialize`; the six remaining commands return it.
- Quota attribution: `sync_quota_from_statusline_file` attributed an observation without `account_id`/`email` to the active account, and `get_agent_metrics` showed (and, through `sync_metrics_to_db`, rewrote) the active account's quota for every agent. The observation must now name a registered account (`resolve_statusline_account`), and an agent's quota comes from the account its process was launched with (`ProcessSupervisor::process_launch_identity`, new); without one, no quota windows.
- `get_agent_metrics(project_path, agent_id, Option<ConversationRef>)`: the conversation id is explicitly ONE-SHIP or native (`ConversationRef`) instead of guessed from its shape (36 chars, `-`, no `conv-`); the `path:agent` key alternative is gone; DB lookups moved to `db_latest_native_session_for_conversation` / `_for_agent` and propagate errors. It is read-only: it no longer calls `sync_metrics_to_db`, which on every UI poll re-upserted the active account's quota with `last_pinged_at = now`, resetting the warmup watcher's "pinged since reset" state. `sync_metrics_to_db` is replaced by `record_session_metrics(metrics, project_id, agent_id, conversation_id)` (no active-account lookup, no fabricated `conv-<pid>-<aid>-default` id), called by `post_agent_response` with the real Conversation id.
- Context window: `RunnerModel.context_window_tokens_count` (new, optional) in the three manifests replaces the substring heuristic (claude/sonnet/opus → 200 000, else 1 048 576). Values checked against published model documentation (2026-11-02): Claude Opus 5.5, Sonnet 5.5 and Fable 5.1 → 1 000 000 (Anthropic docs; the old heuristic assumed 200 000); Gemini 4 Argon, Gemini 3.8 Flash, DeepSeek V4.1 Flash and V4 Pro → 1 048 576; `gpt-oss-120b` → 131 072 (128K; the heuristic assumed 1 048 576). Whether `agy`/`claude` cap Claude below the API window is a pending runtime check. No recorded percentage and no declared window → no context percentage. `max_context_tokens` now carries the window.
- `load_runner_schema` (config.rs): reads only `TEMPLATES_ROOT/runners/<runner>.toml` and returns `Result`; the CWD-relative candidates, the three embedded manifest copies and the `antigravity`/`claudecode` aliases are removed (same decision as `skill.rs`). `TEMPLATES_ROOT` is `pub(crate)`. Callers in `resolution.rs` and `supervisor.rs` log the error and keep their current `Option` logic until those modules are converted.
- Transcript: one path (`.system_generated/logs/transcript.jsonl`, present in all 57 local agy conversations); the root `transcript.jsonl` and `transcript_full.jsonl` candidates are removed; read errors propagate (partial JSON lines are still skipped, as agy appends during reads).
- `set_context_threshold_cmd` deleted: no UI caller (`setContextThreshold` was never invoked), and it replaced an unparsable `rula.toml` with a table holding only the threshold, and returned `Ok` without saving when there was no project or `rula.toml`. `get_context_threshold_cmd` reads the cascade (`accounts.context_warning_threshold_percent`) instead of three tables, two key aliases and a hardcoded 30.0.
- `probe_account_quota`: failed spawns, timeouts and observations without quota returned `Ok(())` (the watcher then emitted `AccountQuotaUpdated`); keyring write and restore and the ping update were discarded; `dup()` results were unchecked. Now each is an error (restore failures logged from the guard), `keyring-warmup-status` is emitted on every outcome, and the poll loop is bounded by `timeout / poll_step`.
- Watcher: `auto_warmup_enabled` (in Settings, never read) now gates warmups; the 5 % threshold, 900 s cooldown, 7000 ms timeout, 150 ms poll and the probe model moved to the `accounts` schema (`quota_depleted_threshold_percent`, `quota_probe_cooldown_seconds`, `quota_probe_timeout_ms`, `quota_probe_poll_step_ms`, `quota_probe_model`). DB and sync work runs on the blocking pool; tick failures are logged.
- `agy_statusline_file_path` fails without a home directory instead of falling back to `/tmp`.
- Dead code removed: `parse_pane_tokens`, `parse_quota_token_value`, `extract_window_stats` (Herder pane scanning; used only by their tests) and those three tests.
- Frontend: `fetchActiveMetrics(projectPath, agentId, conversationId?)` (11 call sites; `ConversationPanel` gets a `refreshMetrics` helper); `setContextThreshold` removed.
- Specs: 19 §2/§3.1/§4, 23 §5 (+ §5.1 warmup configuration), 10 (runner manifests).
